# Notes

How this repository is organized and why. Forge reads this file before every change and keeps it current; so should anyone else who changes the code.

## What it is

A WPILib 2026 Java command-based robot program for a roboRIO, team 4415. It builds, simulates and deploys with the standard WPILib tools (VS Code, or `./gradlew` with the WPILib installation) and depends on nothing from Forge. Phoenix 6 (26.3.0) is in `vendordeps/` for the CTRE devices (Kraken X44 motors on TalonFX).

## The elevator stand

`VCHSRobots/EL-Test-Using-Forge-2026`: Started from the `VCHSRobots/elevator` template repository (now renamed `VCHSRobots/bench-lamp-led`) (without its bench-lamp code).

### The mechanism (facts from the director; keep these here)

- **One stage, 1:1**: the carriage moves exactly as far as the chain. Designed by Micah.
- **Travel: 9.375 in +/- 0.25 in, stop to stop** (measured 15 Nov 2026; an earlier "about 9.5 in" and the old "15 in" are superseded). Zero is the bottom stop.
- **Carriage: 3.959 lb by CAD, without the chains** (an earlier figure was 3.984 lb). Built of 1x2 in aluminium rectangular tube, 1/8 in wall.
- **Drive**: two Kraken X44 drive **one shared shaft**, each through a pinion, an idler and a **46T** gear on the shaft (part CUS-001-068; "068" is a part number, not a tooth count). **The pinions differ: right 15T, left 16T** (director, 15 Nov 2026); the idlers look different sizes (about 1.2 and 1.3 in OD), which fills the different gap and does not change the ratio. So the **right is 46/15 = 3.067** and the **left 46/16 = 2.875 motor turns per shaft turn**. Two #25 chains (0.25 in pitch) on 16T sprockets on that shaft, kept in step by it: **4.0 in per shaft turn**, so **right 0.7667, left 0.71875 motor turns per inch**. Run EL27 measured the right turning 1.065 times the left (16/15 = 1.067), and with these ratios both encoders give the same travel (9.446 and 9.459 in). The motors and gears are at the bottom; the side with them is the back.
- **Motors**: seen from the back, right motor CAN 10 on PDH channel 10, left motor CAN 11 on PDH channel 11, 40 A fuses. The right motor counter-clockwise raises the carriage, the left clockwise. PDH CAN 1, powered through a 120 A breaker; roboRIO 1 on PDH channel 22. CAN: roboRIO -> left -> right -> PDH (terminated).
- **Hard stops** at both ends, thick metal: they can take any force the motors can apply, but **repeated banging will wear the mechanism**, so the code commands heights 0.25 in inside them and only touches them while ranging, gently. **No limit switches.**
- **Goal** (15 Nov 2026): full travel in about 0.5 s, holding within about 0.02 in. Final use: drive it with a joystick, and an autonomous "dance" that runs for minutes.

### How the code runs it

- **Units**: each Talon's `SensorToMechanismRatio` is its own motor turns per inch (`Unit.rightRotationsPerInch()` 0.7667, `leftRotationsPerInch()` 0.71875, from the pinion counts in `KnownUnits`), so the Talons, `ElevatorIO` and `Elevator` all work in **true inches** on both sides (positions, in/s, soft limits, gains). Height is the right encoder; the left is logged too, with `sideDiffInches` (should stay near 0 now).
- **One loop, left follows right** (from 16 Nov 2026, after EL27-EL30): the right Talon runs every request (Motion Magic, open-loop volts) and the left is a CTRE `Follower` of it, `Opposed`, so **both motors always get the same volts**. That is how kS/kG/kV/kA were measured, so the gains are for the pair and the right's slot uses them unscaled (kV 0.0643, no 16/15 factor). The left has no gains and **no soft limits of its own** (so it can never stop following by itself); the right's guard both. History: EL27 was a follower with the wrong right ratio; EL28 ran a Motion Magic loop in each Talon with kP/kD in both (gear slack let the encoders disagree by 0.02-0.1 in and the P terms fought: opposed 35% of the hold, 1 A threshold); EL29 gave the left feedforward only (hold opposed 3%, but the right carried the whole hold); EL30 added the measured feedforward and got worse (descents: left braking +1.4 A against right -0.7 A, opposed 38%; a 17 A, 20 ms left spike as the hold began after ranging). **Expected with the follower**: holding, both carry the same current; moving, the left (16T, spinning 15/16 as fast, less back-EMF) carries about **0.10 A more per in/s** than the right (simulation: 3.9 A at 40 in/s, ~1 A at 10 in/s). That gap is physics, not two loops fighting, and it can make the signs differ briefly on fast descents, when the pair's current is near zero. **On the stand it did not hold**: EL31 had the right carrying more, and later runs showed the split changing between routine starts (see `docs/findings-2026-11-16.md`, the load-sharing fault).
- **Moves: Motion Magic** (`MotionMagicVoltage`) in the right Talon at 1 kHz (the left follows): trapezoid profile (cruise, acceleration, optional jerk), feedforward kS (velocity sign), kG (`Elevator_Static`), kV, kA, plus kP and kD. Every command asks for a height clamped to [0.25 in, travel - 0.25 in]; the Talons' soft limits sit 0.10 in inside each stop.
- **Live tuning** (`Tuning`, `/Elevator/Tuning/`): kS, kG, kV, kA, kP, kD, CruiseInPerSec, AccelInPerSec2, JerkInPerSec3, PeakVolts, StatorAmps, DanceSeconds, DynamicVolts. Each is clamped to a range (ceilings: 12 V, 40 A, 60 in/s, 600 in/s^2) and written into the Talons **only while disabled or parked** (config writes block for up to 50 ms each, harmless with the motors off), so a change takes effect at the next enable, or at once if the stand is parked; a kP/kD sweep therefore runs in one enable: park, write the set, run `moves`, park, next set. `/Elevator/Status/kPInUse` and `kDInUse` show what the Talon has; `ProfileErrorInches` is the height minus the Motion Magic reference, taken from the right Talon's own closed-loop error (sign flipped) so both are from one instant; subtracting the separately read position and reference was ~5 ms skewed and read 0.2 in too high at 25 in/s (sweep run bba8f956, EL32). The values in use are logged (`kS` ... `statorAmps`).
- **Defaults** (`Elevator.DEFAULT_GAINS`): kS 0.12 V, kG 0.16 V, kV 0.0643 V/(in/s), kA 0.0010 V/(in/s^2), for the pair at the same volts, all **measured on EL29** (run cf3877f1, below); kP 8 V/in, kD 0.10 V/(in/s), cruise 10 in/s, acceleration 60 in/s^2; caps 3 V and 20 A. kP 8 / kD 0.10 are confirmed best by the sweep of 16 Nov (run 6ce685c3). The motion limits and caps are still the slow, safe defaults; the fast settings that met the goal (45 in/s, 300-400 in/s^2, 6 V, 40 A) are set by scripts until a PR makes them the default (`docs/next-steps.md`, step 2). With the defaults a full move takes about 1.1 s.
- **Auto-range** (`autoRange`): runs by itself at the first teleop enable after the program starts (and in autonomous, before the dance), again on stick button 1, or as the routine `range`. (1) Creep down at 0.6 V until a stall (speed < 0.3 in/s and >= 6 A for 0.2 s); that is 0 in (`bottomFoundInches` = where it was on the old zero). (2) Motion Magic up to 1.25 in below the nominal top. (3) Creep up at 0.5 V until a stall (>= 8 A); that height is the travel if it is within 0.75 in of 9.375 in, else it fails and keeps the nominal travel (`rangeStatus` FAILED, a DS warning, no automatic retry). The soft limit in the searched direction is off while it searches. Then soft limits go just inside both stops, the stick and the dance span the measured range, and it holds just below the top. Disabling interrupts it (it runs again at the next teleop enable). The encoder zero stays valid while the Talons stay powered, so **nothing re-zeroes while disabled any more**.
- **Teleop**: stick port 0, axis 1 (forward = up): released = bottom of the range (0.25 in), full forward = top of the range. Button 2 toggles the dance.
- **Autonomous**: the dance (`Dance.BEATS`: bounces, a staircase, a shimmy, half bounces; heights as fractions of the measured range; ~20 s a pass) looped for `DanceSeconds` (default 180 s), then to the bottom of the range. It never asks for a height outside the range, so it never touches a stop. Its speed is the Motion Magic tuning.
- **Park, the end of every test** (`park`): a profiled move to the bottom of the range (0.25 in), then the motors off (neutral, brake), `/Elevator/Status/Parked` true and a Driver Station message "Elevator test done: parked at the bottom, motors off. Safe to disable." It stays parked, ignoring the stick, until another routine, a stick button or a disable. With the motors off the carriage may settle the last 0.25 in onto the bottom stop slowly under brake (in simulation it does; on the stand it may hold). Every Forge script writes `park` when it ends, by any ending (`on_exit`), so the person disables whenever convenient and nothing moves after the test; Autonomous parks after the dance. Robot code cannot disable the robot; that stays the person's click.
- **Routines for scripts**: write a name to `/Elevator/Control/Routine` while enabled: `park`, `range`, `moves` (1 -> 8 -> 4.5 -> 1 in, 1.5 s each), `fulltravel` (bottom -> top -> bottom -> top -> bottom of the range, 0.25 in inside each stop, about 8.9 in a move, 1.5 s each; for timing the 0.5 s goal; simulation at 45 in/s, 200 in/s^2: 0.42 s a crossing), `quasistatic` (volts ramp 0.25 V/s up, then down, 1.25 in from the stops; gives kS, kG, kV), `dynamic` (a step of DynamicVolts up, then down; gives kA), `soloright`, `sololeft`, `leftleads` (isolation tests, above), `dance`. It runs when the name changes; write "" to run the same one again. `/Elevator/Status/Routine` is the running command, `RoutinesDone` counts finished ones, plus `PositionInches`, `TargetInches`, `TravelInches`, `Parked`, `ProfileErrorInches`, `kPInUse`, `kDInUse`.
- **Isolation tests** (16 Nov 2026, after run f72f9052 showed the right motor's apparent back-EMF wandering between identical repeats and the left drawing 93% of the energy): `ElevatorIO.Drive` picks which motor leads. `RIGHT_LEADS` is normal; routines `soloright` and `sololeft` run `fulltravel` with ONE motor (the other gets `CoastOut`, no output at all; the leader's kS, kG, kA doubled because it does the pair's work), and `leftleads` runs it with the left leading and the right a `Follower` of it. The leader always gets the gains, Motion Magic and soft limits; the other motor never has soft limits. A switch puts both motors in neutral and rewrites the leader's configs (up to ~200 ms); every ending of those routines, `park`, `range` and any disable put the right back in the lead. Logged: `drive`, `alignedSideDiffInches` (right minus left, both latency-compensated to the same instant, for backlash at reversals), and each motor's active and sticky faults by CTRE's names (`rightFaults`, `leftStickyFaults`, ...; sticky faults are cleared at each drive switch), to name the unexplained fault-field bit 512.
- **Safety**: `/Forge/Abort` true = neutral output for as long as it is true (`aborted`). A lag fault latches (neutral until disabled) if `ProfileErrorInches` is more than 1 in for 0.25 s (judged only while profiling). Nothing moves while disabled; on disable the target becomes the current height.
- **Telemetry**: as before, per motor at 100 Hz (position, velocity, volts, stator/supply/torque current, temperatures, duty, bus volts, closed-loop error/reference/output, faults), plus `mode`, `targetInches`, `profileInches`, `profileVelocityInPerSec`, `profileErrorInches`, `openLoopVolts`, `rangeStatus`, `travelInches`, `danceBeat`, `moveIndex`.
- **Simulation** (`SimElevatorIO`): plain Java, deterministic, 1 kHz. It copies the Talon (Motion Magic trapezoid, no jerk limit, the same feedforward and PD, soft limits, peak volts, a current limit, brake in neutral) and models two Kraken X44 (WPILib `DCMotor`) on the shaft, each with its own gearing from the `Unit` (the simulation unit is geared like the stand), both given the one loop's volts (the left follows) and each drawing its own current, with gravity on the 3.959 lb carriage, 0.28 kg of chain (estimate), Coulomb friction, gravity, back-EMF and moving mass set from the measured kS 0.12 V, kG 0.162 V, kV 0.0643 V/(in/s) (same volts on both) and kA 0.0010 V/(in/s^2), and inelastic hard stops at a settable true travel. Against the data sheet and CAD weight the stand needs 14% more volts for gravity, 9% fewer volts per in/s, and 1.6x the estimated moving mass.
- **Power** (`PowerLog`): reads the PDH (CAN 1) every loop and logs its voltage, total current and watts, channels 10 (right motor), 11 (left motor) and 22 (roboRIO), and its temperature (`pdh*` fields). It is the independent check of the Talons' own supply-current readings and the true battery current; use it for efficiency figures.
- Removed in this version: the 20 ms setpoint ramp, the NetworkTables `TargetInches`/`SpeedInPerSec` control, zero-while-disabled, and the single-motor test pad (port 1).

## Layout

- `src/main/java/frc/robot/Main.java` starts the robot program, or the idle program when built with `-Pprogram=idle`.
- `Robot.java` runs the command scheduler and binds Epilogue logging. It holds nothing else.
- `RobotContainer.java` builds the subsystems from this unit's hardware map and binds the controls.
- `IdleRobot.java` is the idle program: it reports its identity and constructs no motor controller, so enabling it moves nothing. It is left on the robot between sessions.
- `forge/Identity.java` starts the WPILOG log (`DataLogManager`), reads the controller's serial, picks the unit, and publishes the identity (below).
- `hardware/` holds the hardware map: `Unit` is what differs between two units running the same code (CAN IDs, inversions, offsets), and `KnownUnits` lists every physical unit by its roboRIO's serial. An unknown serial gives an unknown unit and a warning on the Driver Station.
- `subsystems/` holds one class per subsystem, each annotated `@Logged` so Epilogue logs its fields. `Elevator` is the only subsystem. `ElevatorView` publishes what AdvantageScope shows under `/Forge/Elevator/`: `Mechanism` (a Mechanism2d), `Components` (the carriage as a robot-relative Pose3d array) and `RobotPose` (always the origin; put it on the Robot row and `Components` on a Component row under it). Display only.
- `assets/Robot_Forge/` is the stand's 3D model for AdvantageScope (`model.glb` the frame, `model_0.glb` the carriage, `config.json`); `assets/README.md` says how to make and show it. The carriage's place along the rails is still off: change `zeroedPosition` in `config.json` and `CARRIAGE_ORIGIN_AT_BOTTOM` in `ElevatorView` together.
- `docs/findings-2026-11-16.md`, `docs/next-steps.md`, `docs/forge-playbook.md`: results, plan and methods from the tuning sessions of 15-16 Nov 2026 (see Status below).
- `tools/analysis/` (`score_crossings.py`, `wpilog.py`) scores runs from Forge's `log_read` CSVs; `tools/forge-scripts/isolation_test.py` is the template for a stand test script. Neither is part of the robot program.
- `docs/sim-and-forge-lessons.md`: lessons from the first simulation sessions (simulator joysticks, the station harness, the 3D model). Read it before simulating or changing the model.
- Repositories: all elevator-stand code lives here. `VCHSRobots/bench-lamp-led` (named `VCHSRobots/elevator` until 15 Nov 2026) is a different, electronics-only bench device (lamp and LED); the model and lessons above were moved here from it on 15 Nov 2026.
- `src/test/java/frc/robot/` holds the scenario tests (`ElevatorScenarioTest`: auto-range from a wrong zero, a rejected travel, ranging on the first teleop enable, goal and default tuning moves with `Metrics`, Abort, the lag fault, the dance, routines by name, characterization staying off the stops, nothing moves disabled; `SimTraceTest` writes `build/sim-trace.csv`): `Scenario` enables the simulated Driver Station, runs the scheduler in 20 ms steps of simulated time, and the test asserts on the subsystems. Nothing here touches a real robot.

## Build identity

The Gradle task `writeBuildConstants` writes `build/generated/sources/forge/java/frc/robot/BuildConstants.java` before every compile: repository, branch, commit, whether the tree was dirty, build time, builder (`FORGE_BUILDER`, else the user name) and program (`robot` or `idle`). At startup the program publishes them to NetworkTables (NT) under `/Forge/Build/` (`Repository`, `Branch`, `Commit`, `Dirty`, `BuiltAt`, `Builder`, `Program`), with `/Forge/Serial` and `/Forge/Unit`, and writes the same as one JSON entry, `/Forge/Identity`, into the WPILOG file. The Forge harness reads these to say which build ran in each run. Built outside a Git checkout, the Git fields are empty.

## Commands

- `./gradlew build` compiles and runs the scenario tests. `./gradlew test` runs only the tests.
- `./gradlew simulateJava` runs the program in simulation with the GUI; add `-Pheadless` for none.
- `./gradlew deploy` deploys to the roboRIO at 10.44.15.2 (or USB). Add `-Pprogram=idle` to build or deploy the idle program.
- After one online build, `--offline` works, as at competition.

## Conventions

- Each subsystem keeps its state in `@Logged` fields and offers commands as factory methods; constants a unit can differ in go in `Unit`, never in the subsystem.
- Every subsystem gets a simulation model in `simulationPeriodic` and at least one scenario test before it runs on hardware.
- Signals are logged through Epilogue and `DataLogManager`, so every run yields comparable WPILOG files.

## The WPILib year

This is the 2026 season: GradleRIO 2026.2.1 (`build.gradle`), `frcYear = '2026'` (`settings.gradle`, which also names the install folder `~/wpilib/2026` or `C:\Users\Public\wpilib\2026`), `projectYear` in `.wpilib/wpilib_preferences.json`, and the `frcYear` in both vendordeps. The roboRIO image, the Driver Station and WPILib must be the same season. To move to 2027:

1. Install that year's WPILib and flash the roboRIO. Set `WPILIB_HOME` for the harness, or change `default_wpilib_home` in `harness/src/forge_harness/config.py`.
2. Set the GradleRIO version, `frcYear` and `projectYear` to the new year. Read the version from the Gradle plugin portal (`edu.wpi.first.GradleRIO`).
3. Replace the vendordeps: `WPILibNewCommands.json` from the `allwpilib` tag of that release, and CTRE's `Phoenix6-frc<year>-latest.json` from `https://maven.ctr-electronics.com/release/com/ctre/phoenix6/latest/`. Delete the old Phoenix file. GradleRIO refuses a vendordep whose year is wrong, which is how you find any you missed.
4. Run `./gradlew build`, then `--offline`. Fix what the new WPILib or Epilogue changed.
